# Local multi-worker development mode (first pass)

This is a packaged localhost mode for exercising distributed-entity behavior in graphical Unity instances. It does not require Docker, WSL, or the C++ AtlasNet node. It is not an AtlasNet production integration.

## Try it in this repository

Use the root `AtlasNetUnity` Unity project, not `Consumer`: `Consumer` currently installs the published Git package and its previously imported sample scripts will not automatically update to these local changes.

1. Open the imported `ScaleDemo` scene under `Assets/Samples/AtlasNet Unity/0.1.0/Simple Authority/Scenes` in each Multiplayer Play Mode window (or equivalent Editor/build instances). The scale scene's camera is top-down orthographic, and the launcher calls `Application.runInBackground = true`.
2. In the first window choose **Start World (Server)**. It should spawn 50 moving cubes and no stationary networked cubes. Only this instance listens on the configured localhost port, 7777 by default.
3. In a second window choose **Join as Worker**. Each server requests and displays its own Voronoi cell as a translucent blue floor region. It receives its authoritative entities, not a fixed border band. Blue cubes are authoritative; amber cubes are interested ghosts. The first server retains the full canonical directory for routing/client ingress but hides distant copies in its sample view.
4. Choose **Join as Client** in a third window. A small green top-down player marker and translucent green interest disk appear; click its Game view and use WASD to move them. The disk shows the entry radius, not the extra exit margin. The `NetworkInterestSource` component on `ScaleInterestPlayer` has an editable 8-unit X/Z entry radius and 1-unit exit padding. The client receives all entities authored by its player's current server; the radius adds nearby entities authored by other servers. Its authoritative worker likewise receives nearby remote entities as ghosts. Watch **Interested ghost visuals** and **Entities** on each server and the client entity count. A late-joining client should start with its own marker, all same-server entities, and nearby cross-server entities. Distant cross-server cubes should appear on entry and disappear after leaving the exit radius; same-server cubes should remain visible regardless of distance. The scale scene does not use the FPS camera.
5. Leave the instances running and move the player across a region boundary. Both moving cubes and the server-authored player can hand off automatically. Their `EntityId` stays fixed as the authority epoch changes. The player's input should continue after the handoff. With two players on one worker, their interest sets are combined without duplicate entity copies.

The launcher also accepts `-atlas-host`, `-atlas-server`, `-atlas-worker`, and `-atlas-client`. Use only instances with matching package and prefab versions. Do not mix this local protocol with the older published package.

For the smaller authority comparison, use `ClientCrossServer` or `ServerCrossServer` from the same sample in every instance. Start a host, then a worker, then a client; alternatively start a server-only window, a worker, and two clients. Consecutive player sessions spawn in alternating worker regions. These scenes have separate player prefabs, a 12-unit interest radius, and automatic handoff enabled. Server/host windows use a top-down orthographic overview: the translucent region is their simulation cell, blue players are authoritative, amber players are interested ghosts, and green disks show locally authoritative players' entry radii. Joined clients keep their first-person camera and see their own interest disk. Move across the boundary, use **F** for the persistent-count/flash/ack RPC example, and watch the entity ID and epoch in the launcher overlay. The cross-server scenes are included in this project's build settings for `-atlas-scene=ClientCrossServer` or `-atlas-scene=ServerCrossServer`. The older single-server authority scenes and prefabs have been removed from the sample.

`PhysicsDemo` now uses the same host/worker/client launch sequence. Its player and three cubes use dynamic Rigidbodies only on their current simulation worker; the player sends movement input and owns its camera aim, not its body pose. Server windows show the top-down region and each player's interest disk. Push a cube while player and cube are on the same worker, then cross a boundary and watch their entity IDs stay fixed while epochs change. Press **R** in a server window to kick that window's authoritative cubes. A cube on another worker is a kinematic ghost here, so cross-worker collision or pushing is **not** implemented. This sample still needs multi-instance Play Mode validation.

## What is real in this pass

- A joining Unity worker is distinguished from a gameplay client; it does not spawn a player. It receives registered-prefab snapshots for entities it simulates and remote entities within the radii of players it simulates. The coordinator adds/removes worker copies when interest changes.
- The first server acts as the local coordinator and client ingress. Workers send entity updates to it; they do not open direct Unity-to-Unity worker connections. Clients keep one logical connection.
- A handoff freezes the source's simulation, serializes its public state plus optional `WriteHandoffState`/`ReadHandoffState` simulation state, prepares the destination, and commits a new authority epoch after acknowledgment. Owner-written transform, variable, and Animator channels continue to arrive at the coordinator during the handoff. The coordinator keeps its latest owner state when importing a worker snapshot and includes that state in the commit, so the destination applies it before gaining simulation authority. Stale worker transform, variable, animator, and RPC updates are rejected by epoch. Input RPCs arriving during a pending handoff are queued and routed to the committed authority.
- `NetworkTransform`, `NetworkVariable`, `NetworkAnimator`, authority RPCs, observer RPCs, and target RPCs have local worker forwarding paths. `NetworkRigidbody` changes between dynamic simulation and kinematic ghost mode and carries velocity across a handoff.
- An authoritative worker can request the coordinator to spawn a registered prefab using `NetworkManager.RequestSpawn(source, prefab, position, rotation, owner)` or despawn an entity with `NetworkObject.Despawn()`. The coordinator verifies the source entity's worker and authority epoch, then assigns a new entity ID and routes the result to clients/workers. Worker spawning is asynchronous and has no immediate return object; the spawned actor initializes in `OnNetworkSpawn`. This keeps identity allocation outside worker gameplay code.
- A server-authoritative entity can call `SendAuthorityFrom(source, nameof(SomeRpc), ...)` on an interested target `NetworkBehaviour` for a `[Rpc(SendTo.Authority, InvokePermission = RpcInvokePermission.Server)]` method. The coordinator validates the source worker/epoch and target ghost residency, then forwards to the target's current authority (or queues during its handoff). This enables a projectile on one worker to update server state on a player simulated by another worker without gameplay code knowing either worker's address.
- The sample overlay shows tick, worker/ghost counts, interested ghost visuals, entity identity, authority epoch, and pending handoffs. The Console logs prepare, commit, abort, and worker disconnects. The scale sample moves cubes across X/Z regions automatically; no gameplay code selects a destination worker.
- `ScaleRegionOverlay` requests diagnostic geometry once and receives changes when workers join or leave. Geometry is optional and is never consulted for simulation permission by sample gameplay code.

## Important boundaries

- This first pass has passed a C# compile and local protocol/region checks, **not** a Unity multi-instance runtime smoke test. A successful visual handoff must be confirmed in the Editor/builds before relying on it.
- Worker interest is a local, player-centered approximation. Each authoritative player supplies a radius; the coordinator uses region overlap to skip irrelevant source regions and checks each candidate entity's X/Z distance before delivering it. The existing-ghost exit margin reduces edge churn. This works with nonadjacent interested workers; the region boundary does not itself create ghosts. The first server still retains all canonical entities and client ingress; its distant routing copies are hidden in the sample view. The translucent cell marks simulation authority; amber copies are read-only ghosts.
- This does **not** implement production AtlasNet interest, source-worker query/culling, line of sight, or distributed collision. The local coordinator currently knows every entity and performs the worker/client subscription filtering; a later backend must provide the discovery and subscription/delta exchange. The client always receives entities from its player's authoring worker, with the radius applying only to other workers. A player prefab without `NetworkInterestSource` still observes the full world unless explicitly hidden. The radius is a demo cross-server proximity rule, not a general visibility or security policy.
- A disconnected worker's committed entities are deliberately frozen; there is no lease-based failure recovery or persistence. Uncommitted handoffs time out and resume the source when possible.
- The first server is a single coordination and client-ingress process. This does not yet demonstrate AtlasNet C++ node communication, multiple client connections, cross-node transport selection, production interest filtering, or distributed PhysX contacts.
- Automatic spatial handoff targets entities with a synchronized root position written by either the server or an owning client. The owning client's movement writer does not change when the simulation worker changes; only server-side state and entity-directed RPC routing move. `ClientCrossServer` and `ServerCrossServer` both include `NetworkInterestSource` and enable automatic handoff. Voronoi seeds remain stable after other workers join, so cell areas are approximate rather than guaranteed equal. A new worker also claims existing entities in its newly formed region; subsequent transfers occur as entities cross boundaries.
- This localhost wire protocol is versioned only for matching local instances; worker spawn/despawn and optional client debug-region messages require protocol version 8 in every instance. It is not the final C++/C# ABI. See `AuthorityBackendContract.md` for the expected semantic ownership, handoff, residency, and optional debug exchange. The Unity gameplay API remains independent of transport and worker addresses.

## Reusable local debug view

`Samples~/SimpleAuthority/Prefabs/LocalDebugView.prefab` is a local-only sample prefab. Place one scene instance beside `NetworkManager`; do not register or spawn it as a network entity. Servers show a top-down view automatically, including their region fill, authoritative/ghost markers, and visible players' cross-worker interest radii. Middle-mouse drag pans this server camera and the wheel zooms; it does not recenter after navigation. A joined client can press **F8** to show or hide only its own cross-worker interest radius and current simulation worker's region in the normal first-person view. The client toggle never creates, moves, or replaces its gameplay camera. Camera height, initial server size, and floor-overlay height are editable on the prefab for different maps.

The client subscribes to its owned entity's region only while the overlay is enabled. The local coordinator verifies ownership and sends only that worker's polygon; it updates the outline after handoffs and region topology changes. This is optional diagnostic data, not a gameplay authority or visibility rule. The radius does not bound same-worker visibility, and production AtlasNet may provide no geometric region at all. The prefab uses the sample's `ScaleRegion` and `ScaleInterest` materials/shader, which support URP and the built-in render pipeline; copy or import those assets with it.
