# Local multi-worker development mode (first pass)

This is a packaged localhost mode for exercising distributed-entity behavior in graphical Unity instances. It does not require Docker, WSL, or the C++ AtlasNet node. It is not an AtlasNet production integration.

## Try it in this repository

Use the root `AtlasNetUnity` Unity project, not `Consumer`: `Consumer` currently installs the published Git package and its previously imported sample scripts will not automatically update to these local changes.

1. Open the imported `05_InterestAndScale` scene under `Assets/Samples/AtlasNet Unity/<version>/05 InterestAndScale` in each Multiplayer Play Mode window (or equivalent Editor/build instances). The scale scene's camera is top-down orthographic, and the launcher calls `Application.runInBackground = true`.
2. In the first window choose **Start World (Server)**. It should spawn 50 moving cubes and no stationary networked cubes. Only this instance listens on the configured localhost port, 7777 by default.
3. In a second window choose **Join as Worker**. Each server requests and displays its own Voronoi cell as a translucent blue floor region. It receives its authoritative entities, not a fixed border band. Blue cubes are authoritative; amber cubes are interested ghosts. During handoff, red marks an entity exiting this server and green marks one entering it. Green remains briefly after commit for readability; these local-only colors do not delay or drive the transfer. The first server retains a data-only directory for routing/client ingress; a distant entity should no longer have a Unity `NetworkObject` there.
4. Choose **Join as Client** in a third window. A small green top-down player marker and translucent green interest disk appear; click its Game view and use WASD to move them. The disk shows the entry radius, not the extra exit margin. The `NetworkInterestSource` component on `ScaleInterestPlayer` has an editable 8-unit X/Z entry radius and 1-unit exit padding. The client receives all entities authored by its player's current server; the radius adds nearby entities authored by other servers. Its authoritative worker likewise receives nearby remote entities as ghosts. Watch **Interested ghost visuals**, **Tracked IDs**, and **Local replicas** on each server. On the first server, tracked IDs should remain global while local replicas drop after out-of-interest handoffs; those removed copies should have no collider or simulation updates. A late-joining client should start with its own marker, all same-server entities, and nearby cross-server entities. Distant cross-server cubes should appear on entry and disappear after leaving the exit radius; same-server cubes should remain visible regardless of distance. The scale scene does not use the FPS camera.
5. Leave the instances running and move the player across a region boundary. Both moving cubes and the server-authored player can hand off automatically. Their `EntityId` stays fixed as the authority epoch changes. The player's input should continue after the handoff. With two players on one worker, their interest sets are combined without duplicate entity copies.

The launcher also accepts `-atlas-host`, `-atlas-server`, `-atlas-worker`, and `-atlas-client`. Use only instances with matching package and prefab versions. Do not mix this local protocol with the older published package.

For the smaller authority comparison, use `02_ClientAuthority` or `03_ServerAuthority` from the same sample in every instance. Start a host, then a worker, then a client; alternatively start a server-only window, a worker, and two clients. Consecutive player sessions spawn in alternating worker regions. These scenes have separate player prefabs, a 12-unit interest radius, and automatic handoff enabled. Server/host windows use a top-down orthographic overview: the translucent region is their simulation cell, blue players are authoritative, amber players are interested ghosts, and green disks show locally authoritative players' entry radii. Joined clients keep their first-person camera and see their own interest disk. Move across the boundary, use **F** for the persistent-count/flash/ack RPC example, and watch the entity ID and epoch in the launcher overlay. The cross-server scenes are included in this project's build settings for `-atlas-scene=02_ClientAuthority` or `-atlas-scene=03_ServerAuthority`. The older single-server authority scenes and prefabs have been removed from the sample.

`04_Physics` now uses the same host/worker/client launch sequence. Its player and three cubes use dynamic Rigidbodies only on their current simulation worker; the player sends movement input and owns its camera aim, not its body pose. Server windows show the top-down region and each player's interest disk. Push a cube while player and cube are on the same worker, then cross a boundary and watch their entity IDs stay fixed while epochs change. Press **R** in a server window to kick that window's authoritative cubes. Copies on clients or other workers remain kinematic; contact impulses are not forwarded.

## Dummy partition configuration

On NetworkManager, assign **Dummy Backend Partitioning > Partition Center**. The coordinating server samples this Transform position at session start; leaving it empty uses world zero. Its rotation and scale do not affect the split. All ownership and interest queries use unbounded Voronoi cells in the dummy backend. **Debug View Extent** only crops the optional diagnostic polygons; keep it beyond the camera viewing distance for an apparently continuous boundary. Unity performs normal frustum and triangle clipping on the debug mesh. The shipped samples include a **Dummy Partition Center** Transform.

Equal shares mean equal sectors around the center, so a circular area has equal shares at every radius. Cropping three sectors to a square does not produce three equal-area finite triangles. This is a spatial demonstration, not a CPU-load balancer. Seed redistribution can transfer existing entities through the normal handoff protocol; the Unity-facing manager and sample scripts do not choose worker ownership.

## What is real in this pass

- A joining Unity worker is distinguished from a gameplay client; it does not spawn a player. It receives registered-prefab snapshots for entities it simulates and remote entities within the radii of players it simulates. The coordinator adds/removes worker copies when interest changes.
- The first server acts as the local coordinator and client ingress. Workers send entity updates to it; they do not open direct Unity-to-Unity worker connections. Clients keep one logical connection.
- A handoff freezes the source's simulation, serializes its public state plus optional `WriteHandoffState`/`ReadHandoffState` simulation state, prepares the destination, and commits a new authority epoch after acknowledgment. Owner-written transform, variable, and Animator channels continue to arrive at the coordinator during the handoff. The coordinator keeps its latest owner state when importing a worker snapshot and includes that state in the commit, so the destination applies it before gaining simulation authority. Stale worker transform, variable, animator, and RPC updates are rejected by epoch. Input RPCs arriving during a pending handoff are queued and routed to the committed authority.
- `NetworkTransform`, `NetworkVariable`, `NetworkAnimator`, authority RPCs, observer RPCs, and target RPCs have local worker forwarding paths. `NetworkRigidbody` changes between dynamic simulation and kinematic ghost mode and carries velocity across a handoff.
- An authoritative worker can request the coordinator to spawn a registered prefab using `NetworkManager.RequestSpawn(source, prefab, position, rotation, owner)` or despawn an entity with `NetworkObject.Despawn()`. The coordinator verifies the source entity's worker and authority epoch, then assigns a new entity ID and routes the result to clients/workers. Worker spawning is asynchronous and has no immediate return object; the spawned actor initializes in `OnNetworkSpawn`. This keeps identity allocation outside worker gameplay code.
- A server-authoritative entity can call `SendAuthorityFrom(source, nameof(SomeRpc), ...)` on an interested target `NetworkBehaviour` for a `[Rpc(SendTo.Authority, InvokePermission = RpcInvokePermission.Server)]` method. The coordinator validates the source worker/epoch and target ghost residency, then forwards to the target's current authority (or queues during its handoff). This enables a projectile on one worker to update server state on a player simulated by another worker without gameplay code knowing either worker's address.
- The sample overlay shows tick, worker/ghost counts, interested ghost visuals, entity identity, authority epoch, and pending handoffs. The Console logs prepare, commit, abort, and worker disconnects. The scale sample moves cubes across X/Z regions automatically; no gameplay code selects a destination worker.
- `ScaleRegionOverlay` requests diagnostic geometry once and receives changes when workers join or leave. Geometry is optional and is never consulted for simulation permission by sample gameplay code.

## Important boundaries

The local implementation now lives behind `IWorldBackend` in `LocalWorldBackend.cs` and `LocalWorldBackend.Workers.cs`; `NetworkManager` remains the Unity component. See `AuthorityBackendContract.md` for the current transition rules. The proposed epoch of an aborted attempt is never reused, so committed epochs can skip numbers on retry. This refactor has standalone compile and transition checks; it still needs the interactive multi-instance checks below.

- The directory/replica refactor has passed a C# compile, **not** a Unity multi-instance runtime smoke test. Confirm first-server eviction, late joins, owner-written state, RPCs, handoff in both directions, and collider removal in Editor/build instances before relying on it.
- Worker interest is a local, player-centered approximation. Each authoritative player supplies a radius; the coordinator uses region overlap to skip irrelevant source regions and checks each candidate entity's X/Z distance before delivering it. The existing-ghost exit margin reduces edge churn. This works with nonadjacent interested workers; the region boundary does not itself create ghosts. The first server retains directory records for all entities but Unity copies only for its authority, local interest, host-client view, or a pending handoff. The translucent cell marks simulation authority; amber copies are read-only ghosts.
- `NetworkManager.SpawnedCount`, `SpawnedObjects`, and `TryGet` now describe that instance's resident Unity objects, not the global entity count. On the first server, a missing `TryGet` result for a remote out-of-interest entity is expected while its directory entry continues to route packets and serve late-join snapshots. The local relay receives replaceable full worker snapshots at approximately 5 Hz using per-entity unreliable sequencing. Transform updates, lifecycle messages, and handoff transactions retain reliable ordering. The Unity Transport adapter batches small reliable messages into frames capped at 1,100 bytes so state traffic does not consume a separate reliable packet window entry per entity update. A send-only LateUpdate phase flushes messages created during gameplay in the same frame, without rerunning receive callbacks. Failed sends stay in the ordered message queue and are repacked together with new messages on retry, still under the same cap; large individual messages use transport fragmentation. Late snapshots from a previous authority epoch are ignored.
- This does **not** implement production AtlasNet interest, source-worker query/culling, line of sight, or distributed collision. The local coordinator currently knows every entity and performs the worker/client subscription filtering; a later backend must provide the discovery and subscription/delta exchange. The client always receives entities from its player's authoring worker, with the radius applying only to other workers. A player prefab without `NetworkInterestSource` still observes the full world unless explicitly hidden. The radius is a demo cross-server proximity rule, not a general visibility or security policy.
- A disconnected worker's committed entities are deliberately frozen; there is no lease-based failure recovery or persistence. Uncommitted handoffs time out and resume the source when possible.
- The first server is a single coordination and client-ingress process. This does not yet demonstrate AtlasNet C++ node communication, multiple client connections, cross-node transport selection, production interest filtering, or distributed PhysX contacts.
- Automatic spatial handoff targets entities with a synchronized root position written by either the server or an owning client. The owning client's movement writer does not change when the simulation worker changes; only server-side state and entity-directed RPC routing move. `02_ClientAuthority` and `03_ServerAuthority` both include `NetworkInterestSource` and enable automatic handoff. The dummy backend repositions all seeds at equal angular spacing around its configured center whenever workers join or leave. Two simulation workers form half-planes, three form 120-degree wedges, and four form quadrants. The coordinator counts as a simulation worker. A new worker also claims existing entities in its newly formed region; subsequent transfers occur as entities cross boundaries.
- This localhost wire protocol is versioned only for matching local instances; the current runtime uses protocol version 18 in every instance. It is not the final C++/C# ABI. See `AuthorityBackendContract.md` for the expected semantic ownership, handoff, residency, and optional debug exchange. The Unity gameplay API remains independent of transport and worker addresses.

## Local debug overlays

The optional Shared sample contains  `ScaleRegionOverlay` and `ScaleInterestOverlay` for worker and interest diagnostics, plus `ClientBoundaryOverlay` for nearby client boundary walls. These are local-only sample components, not network entities or required runtime features. Use the imported scenes and `AtlasNetManager.prefab` as configuration references.

The client boundary overlay subscribes to its owned entity's region only while enabled. The coordinator verifies ownership and updates the region after handoffs and topology changes. Its view radius limits diagnostic geometry, not gameplay visibility. This optional debug data comes from the backend; production AtlasNet may provide no geometric region.

## Checking the backend refactor

1. Refresh the Unity project so the new runtime source files import. Let Unity generate their meta files.
2. Start a server, worker, and two clients in `02_ClientAuthority`, then repeat in `03_ServerAuthority`. Verify move/look/jump, F-key state/flash/ack delivery, and a late join after changing the persistent value.
3. Cross a boundary repeatedly while sending F-key events. Entity ID and owner stay unchanged, committed epochs increase, only one worker simulates, and pending transfers return to zero. Leave interest and re-enter; distant replicas and colliders should disappear and return with current state.
4. Stop the destination worker during a pending transfer. The surviving source should resume after abort. Stop the source instead; confirm the entity freezes and logs the unsupported recovery condition.
5. Repeat in `04_Physics` for velocity continuity, same-worker pushing, and kinematic ghosts. Cross the Voronoi boundary and verify the simulation worker and epoch change while the entity ID is retained.
6. In `05_InterestAndScale`, enable **Log metrics every 5 seconds** on each instance (or pass `-atlas-metrics` in builds). Record role, worker, tick, tracked/resident/authority/ghost counts, pending handoffs, tick milliseconds, allocation bytes, and bytes sent per tick. These are sampled individual ticks, not interval averages or percentile benchmarks. Compare equivalent worker/client counts and movement conditions before drawing scaling conclusions.

Automated transition checks run with `dotnet run --project Packages/com.atlasnet.unity/Tests~/Standalone/AtlasNetChecks.csproj` from the repository, using .NET 10 and the installed Unity 6000.6.2f1 managed assemblies. For another installation, pass `-p:UnityEditorPath="C:/path/to/Unity/version"`. This hand-authored test project lives in `Tests~` so Unity does not import its standalone entry point. It compiles runtime/sample sources and covers early/wrong ACKs, stale or duplicate exports, aborted-attempt epochs, timeouts across tick wrap, and epoch overflow, plus the existing codec, local TCP, and Voronoi checks. It does not replace these Unity runtime checks or supply current performance measurements.

### Physics across workers

Physics bodies retain ordinary per-object spatial authority. There are no contact groups or fixed shared regions. Server-authoritative player bodies (an owned NetworkObject with server-written NetworkRigidbody) can push unowned server props across a worker boundary automatically. The player's native contact with the kinematic prop copy generates a bounded requested push velocity from contact closing speed, not from solver impulses. The existing server-only entity-interaction RPC routes this intent to the prop's authority. In FixedUpdate, limited force converges toward that speed without accelerating past it. Duplicate requests replace intent, short expiry stops stale intent, and the matching remote-player proxy collision is disabled to prevent double response. Ground pushes follow the gravity plane. Co-located bodies use native PhysX collisions only.

The manager sends nearby kinematic server-body replicas to workers for contact discovery; this does not expand gameplay-client interest. Recent remote pushes briefly retain the prop's authority, while player placement remains independent. Source/target epochs, source identity, finite values, and proximity are checked. Handoffs clear buffered forces, and collision ignores are restored when authority changes or entities leave. NetworkRigidbody supplies automatic defaults: maximum remote push speed 3 m/s and force 30 N per player. Existing gameplay scripts and prefabs require no changes.

`CrossWorkerPhysicsTests` uses isolated physics scenes and actual worker transport to check remote player/box contact, opposed players on separate workers, stale source/target epochs, invalid values, bounded convergence and stationary overlap, and ordinary movement handoffs. This is approximate pushing at the center of mass; it is not a shared contact solver or a solution for cross-worker stacks and friction.

`07_ClientPhysics` remains an owner-written Rigidbody control sample. Client-owned bodies do not send these trusted-server pushes; client-side prediction/interaction requests remain outside this pass. The local protocol is version 18: rebuild older players before connecting them.
